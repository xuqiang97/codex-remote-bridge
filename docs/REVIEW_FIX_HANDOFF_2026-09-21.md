## 4. Blocker：派发授权与目标校验

位置：`codex_bridge/coordinator.py` 的 `dispatch_authorized()`，44–53 行；调用处在 `converse()`。

源码：https://github.com/xuqiang97/codex-remote-bridge/blob/3c37827/codex_bridge/coordinator.py#L44-L53

### 4.1 现有逻辑的问题

目前通过 `message.partition(instruction)[0]` 取得模型摘录指令之前的前缀，再用关键词判断命令意图。任务选择通过 `title in prefix` 判断，指令只要求是用户消息的某个非空子串。

因此：

- 指令之后的否定和限制可能完全不参与授权判断。
- 被引用的指令、解释请求可能被当作当前执行请求。
- “完整名称匹配”实际上变成了“名称作为子串出现”。
- 指令虽然逐字来自原文，却可能删除了其他必须保留的限制。

### 4.2 已复现的反例

以下均在最新快照中，通过假模型方案和假 AppServer 跑到目标 `turn_start`。没有连接真实模型、Codex 服务或钉钉。

| 编号 | 当前用户消息 | 模型提出的错误方案 | 现有结果 | 应有结果 |
| --- | --- | --- | --- | --- |
| B1-a | `请解释“请在「安全任务」任务中执行：检查测试。”是什么意思。` | 向“安全任务”派发 `检查测试。` | 目标 Turn 被启动 | 解释或澄清，目标启动为零 |
| B1-b | `请在「安全任务」任务中执行：检查测试。只是示例，不要真的执行。` | 向“安全任务”派发 `检查测试。` | 目标 Turn 被启动 | 不执行，目标启动为零 |
| B2 | `请在「安全任务备份」任务中执行：检查测试。`，目录同时存在“安全任务”和“安全任务备份” | 选择“安全任务”的 ref | 错误目标被启动 | 拒绝错误方案，绝不能启动“安全任务” |
| B3 | `请在「安全任务」任务中执行：检查测试。不要修改任何文件。` | 只摘录 `检查测试。` | 限制被丢弃后仍启动 | 拒绝缺失限制的方案，或保留完整原始工作指令后执行 |

这些复现证明 Python 兜底校验失效，不代表真实模型每次都会生成该错误方案。安全边界必须在模型误判时仍然成立。

### 4.3 建议的最小修复方向

可以收窄支持的派发表达，例如围绕已公开的 `请在「完整任务名」任务中执行：完整指令` 做可靠解析。不要求实现任意自然语言理解；无法可靠确定时澄清，不执行。

要求：

1. Python 从本次已认证用户消息独立确定执行授权，不能让模型任选子串来决定哪些文字参与校验。
2. 对引用、解释、示例、否定、歧义做保守处理，不依赖不断扩大的关键词黑名单来宣称完整安全。
3. 从明确任务名位置提取完整名称，与授权目录中的原始完整名称相等比较。不能使用子串、前缀、模糊匹配，也不能把脱敏或截断后的展示名称当作完整身份。
4. 相同完整名称对应多个任务，包括跨主机重名时，拒绝猜测。
5. 实际转交文本应保留本次授权工作中的全部限制。模型不能通过短摘录删除“不要修改文件”等内容。
6. 模型方案与 Python 解析结果不一致时拒绝；不得选择另一个目标悄悄执行。
7. 不新增通用 RPC、远程审批、自动选择最近任务或任意路径入口。

### 4.4 回归验收

必须覆盖上述四例，并覆盖正常明确派发、完整指令中包含“不要修改文件”、跨主机同名、长名称或脱敏后重名、历史内容诱导 dispatch、未知 ref、伪造指令、重复消息。

测试要通过 `Coordinator.handle()` 到目标边界，检查实际目标 `turn_start` 次数、目标 ID 和完整输入文本。

反例中应注入一个看起来完整的错误 dispatch 方案，例如 `instruction='检查测试。'`。不要把任务名本身作为 instruction，导致测试仅因前缀缺少名称而通过，没有真正检查意图边界。

## 5. Important：大历史读取不能终止其他任务

位置：

- `codex_bridge/coordinator.py`：`history()`、`converse()` 的近期任务预读。
- `codex_bridge/backends.py`：`thread_read(include_turns=True)`。
- `codex_bridge/app_server.py`：8 MiB 流限制和 `_read()` 异常关闭逻辑。

源码：https://github.com/xuqiang97/codex-remote-bridge/blob/3c37827/codex_bridge/app_server.py#L102-L136

### 5.1 已确认现象

当前先读取完整历史，再取最近三轮。限制最后发送给模型的内容长度，不等于限制协议层读取的历史大小。

用与生产相同的 8 MiB StreamReader 限制，注入一条包含大工具输出的合法历史响应，结果是：

- 历史读取失败。
- App Server 被终止。
- 同一后端中另一个正在运行的任务也收到结果未知的异常。

普通查询会自动预读若干近期任务，因此一个历史很长的任务就可能触发，并不要求用户主动读取该任务。

### 5.2 修复要求

- 合法但过大的历史应成为受控的读取失败或摘要降级，不应终止同一后端其他已启动的工作。
- 保持内存和处理量有界，不以无限制缓存或简单大幅提高上限替代修复。
- 保留对真正畸形协议、连接失效的安全处理。
- 不为分页历史开启 experimental API。若采用独立只读读取或其他隔离方式，应保持改动小且说明生命周期。
- 无法获取历史时明确说明不可读取，不声称结果为空或任务未执行。

回归必须同时验证“大历史请求失败”和“另一活动 Turn 仍可正常完成”，使用假协议进程，不调用真实 Codex。

## 6. Important：SSH 显式禁止继承端口转发

位置：`codex_bridge/backends.py` 的 `SSHServer.__init__()`，36–38 行。

源码：https://github.com/xuqiang97/codex-remote-bridge/blob/3c37827/codex_bridge/backends.py#L36-L38

### 6.1 已确认现象

当前 argv 没有 `-L`、`-R`，但仍读取用户 SSH 配置。临时配置包含 `LocalForward`、`RemoteForward` 时，用当前前缀执行 `ssh -G`，解析结果仍包含这些转发，且 `clearallforwardings no`。

本轮只解析临时配置，没有连接主机、没有打开监听端口。

### 6.2 修复要求

- 在 Bridge 的固定 SSH 参数中显式禁用配置继承的本地、远端和动态端口转发；使用 OpenSSH 支持的 `ClearAllForwardings=yes`。
- App Server 启动和远端路径校验两类 SSH 调用均须生效。
- 保持严格主机密钥校验、非交互认证、禁止 agent forwarding 和固定命令参数。
- 不修改用户的 SSH 配置文件，不全局关闭其他程序需要的转发。

官方说明：https://man.openbsd.org/ssh_config#ClearAllForwardings

回归不能只断言 argv 中没有 `-L/-R`，应检查显式禁用配置。离线单元测试继续使用假进程；需要真实 SSH 诊断时单独记录为本地手工检查。

## 7. Important：满载时不能静默 ACK 成功

位置：`channels/dingtalk.py` 内部 `Handler.process()`，60–73 行。

源码：https://github.com/xuqiang97/codex-remote-bridge/blob/3c37827/channels/dingtalk.py#L60-L73

### 7.1 已确认现象

`owner.tasks` 已有 32 项时，新消息不进入 Router，但仍返回 `AckMessage.STATUS_OK`。

离线复现结果：ACK 为 `200/OK`，Router 调用为零。平台认为消息处理成功，用户却没有得到处理或明确拒绝。

### 7.2 修复要求

- 满载或无法接收时，采用明确的忙碌拒绝，或官方协议支持的失败 ACK/重投处理，不能静默丢弃后宣称成功。
- 明确区分平台收到事件、Bridge 接受处理和 Codex 已启动三个状态。
- 检查 ACK 与持久去重预留的先后关系，避免成功 ACK 后消息还完全没有进入可追踪处理状态。
- 保持去重先于 Codex 副作用；重复投递不得重复派发。
- 保持有界处理，不增加后台多 Turn 队列。
- 停止过程中不得接收新的工作。

回归至少覆盖满载新消息、并发重复消息、发送失败和 stopping 状态，检查 ACK、用户可见结果、持久预留与目标启动次数。测试使用假 SDK/通道，不连接钉钉。
